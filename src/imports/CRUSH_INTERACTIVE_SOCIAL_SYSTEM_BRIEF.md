# CRUSH INTERACTIVE — SOCIAL SYSTEM BRIEF

## Working Document

This document defines the current understanding, source material, constraints, visual references, and design goals for creating a flexible social content system for Crush Interactive.

This is NOT an existing Crush Social Design System.

It is a working brief intended to help analyze the available material and define the system that should be built.

The final Social Design System, component architecture, compositions, and templates do not exist yet and should emerge from this process.

---

# 01 — PROJECT OBJECTIVE

Create a flexible visual system for Crush Interactive social content.

The system should allow the team to create different types of Instagram content while maintaining a recognizable Crush Interactive identity.

The goal is NOT to create a collection of fixed Instagram posts.

The goal is to create a reusable visual language that can generate different compositions, content types, and visual treatments without requiring a complete redesign every time.

Core principle:

FLEXIBLE SYSTEM = REUSABLE VISUAL LANGUAGE

NOT:

FLEXIBLE SYSTEM = DESIGN ANYTHING FOR EACH CLIENT

---

# 02 — WHAT WE ARE TRYING TO SOLVE

The current Crush material shows multiple visual approaches.

These approaches should not automatically become separate design systems.

Instead, the system should identify:

- what remains consistently Crush;
- what can change;
- what belongs to a specific content series;
- what belongs to a visual treatment;
- what belongs to a composition;
- what is project-specific;
- what should remain outside the core system.

The final system should provide enough structure to maintain consistency while allowing enough flexibility to avoid repetitive or generic content.

# 04 — SOURCE CLASSIFICATION

All information used during the system definition should be classified into one of four categories.

## ESTABLISHED

Information explicitly defined by the official Crush Interactive Brand Guidelines.

These should be treated as existing brand rules.

## OBSERVED

Visual patterns visible in the provided Crush references.

These are real examples of existing work, but they are not automatically official system rules.

## PROPOSED

Potential structures, components, compositions, or system rules inferred from the available material.

These require validation.

## HYPOTHESIS

Possible relationships or classifications that still need to be investigated.

Examples:

- whether Black Design should be a visual mode;
- whether Social Post should be a content series;
- whether Original Design should be a composition family;
- how client adaptation should work.

Do not present PROPOSED or HYPOTHESIS information as an existing Crush standard.

---

# 05 — EXISTING VISUAL REFERENCES

The current working references include four visual territories:

1. Original Design
2. Black Design
3. Social Post
4. Adapted Design

These are existing references, not four approved design systems.

The system should analyze their similarities and differences before determining their final role in the architecture.

Do not assume that each reference needs to become a separate system.

---

# 06 — ORIGINAL DESIGN

Original Design represents one of the main editorial and brand-driven visual directions.

Characteristics observed:

- strong typography;
- large headlines;
- black and/or warm light backgrounds;
- Crush Orange as an accent;
- photography;
- website screenshots;
- graphic annotations;
- doodles;
- lines;
- overlays;
- layered compositions;
- editorial layouts;
- collage-like compositions;
- strong visual hierarchy.

This should be treated as an important reference for the core Crush visual language.

The system should determine which characteristics are reusable and which are specific to individual examples.

---

# 07 — BLACK DESIGN

Black Design represents a darker expression of the Crush visual language.

Characteristics observed:

- dark or black backgrounds;
- high contrast;
- large typography;
- white typography;
- Crush Orange accents;
- editorial/poster feeling;
- large statements;
- screenshots and mockups;
- graphic overlays;
- strong visual impact.

Do not automatically treat Black Design as a separate design system.

Investigate whether it is better represented as:

- a visual mode;
- a composition family;
- a treatment;
- or another reusable system layer.

Do not make every Crush piece dependent on black backgrounds or heavy gradients.

---

# 08 — SOCIAL POST

Social Post represents a different type of social content behavior.

Examples include the "Cafecito with Crush" style of content.

Characteristics observed:

- real photography;
- people and relationships;
- events;
- cafés;
- networking;
- team/client interactions;
- documentary feeling;
- recurring branding;
- Crush logo;
- orange graphic elements;
- recognizable recurring title/series treatment.

This should not automatically be treated as another general-purpose visual system.

Investigate whether it should instead be represented as:

- a content series;
- a social/documentary treatment;
- a visual mode;
- or a combination of these.

---

# 09 — ADAPTED DESIGN

Adapted Design represents a more client-specific visual treatment.

Examples show:

- client-specific color palettes;
- client-specific imagery;
- illustrations or graphic elements related to the client's industry;
- stronger integration between Crush and the client's visual world;
- project-specific art direction.

This direction is intentionally NOT part of the first core system build.

Treat it as:

FUTURE / ADVANCED FLEXIBILITY

The first version should not optimize for unlimited client-specific visual customization.

Important principle:

CLIENT ADAPTATION SHOULD NOT REDEFINE THE CRUSH SYSTEM.

If this capability is explored later, it should happen through controlled extensions of the system rather than by creating a completely new visual identity for every client.

---

# 10 — FLEXIBILITY PRINCIPLE

The concept of flexibility is important to the broader Crush creative direction.

A reusable system should not force every piece into the same structure.

Different content should be able to emphasize different things.

The system should allow:

- different content priorities;
- different compositions;
- different amounts of text;
- different image treatments;
- different screenshot treatments;
- optional sections;
- different storytelling approaches;
- different visual emphasis.

However, flexibility must happen inside the Crush visual language.

The goal is:

REUSABLE SYSTEM + CONTROLLED VARIATION

NOT:

FIXED TEMPLATE

and NOT:

UNCONTROLLED CUSTOM DESIGN

# 22 — VARIANTS AND PROPERTIES

Use variants only when they represent meaningful structural differences.

Good example:

Screenshot:

- Single;
- Desktop + Mobile;
- Multiple Screens;
- Before;
- After.

Bad example:

Creating many variants that only change:

- text;
- image;
- minor spacing;
- arbitrary decorative details.

Content should remain content.

Structure should remain structure.

---

# 23 — DESIGN TOKENS

Investigate a token structure for:

- color;
- typography;
- spacing;
- radius;
- borders;
- image treatments;
- composition values where useful.

Tokens should make the system easier to modify.

Do not create an unnecessarily large token architecture.

The goal is practical reuse.

# 24 — WHAT FLEXIBILITY MEANS

Flexibility should operate at several levels.

### Level 1 — Content

Change:

- headline;
- image;
- screenshot;
- quote;
- project;
- message.

### Level 2 — Story

Change what the piece emphasizes:

- transformation;
- visual;
- experience;
- people;
- result;
- project;
- education;
- social.

### Level 3 — Composition

Change:

- image position;
- text position;
- number of screens;
- layout;
- density;
- visual hierarchy.

### Level 4 — Visual Treatment

Potentially change between:

- editorial/light;
- dark/black;
- social/documentary.

These are hypotheses to validate, not fixed categories.

### Level 5 — Format

Adapt to:

- 1:1;
- 4:5;
- 9:16.

This hierarchy should allow variation without breaking the system.

---

# 25 — WHAT FLEXIBILITY DOES NOT MEAN

The system should NOT:

- create a new visual identity for every client;
- automatically replace the Crush brand palette;
- replace Crush typography with arbitrary client typography;
- create unlimited decorative styles;
- make every project completely custom;
- turn every piece into a different design language;
- optimize for Adapted Design during the first build.

Client-specific visual adaptation is a future extension.

---

# 27 — DO NOT ASSUME THE FINAL ARCHITECTURE

The purpose of the first AI exploration is to analyze the available material and propose the most useful architecture.

Do not force the following categories if the evidence suggests another structure:

- components;
- blocks;
- compositions;
- visual treatments;
- story types;
- templates.

The AI should identify relationships between them.

The system should emerge from the actual Crush material.

# 30 — ADAPTED DESIGN: FUTURE EXPERIMENT

Adapted Design may eventually become an extension of the system.

The future question is:

"How much can a client/project influence the visual treatment while the content still clearly belongs to Crush Interactive?"

Potential future adaptation layers could include:

- controlled color substitution;
- client-specific graphic motifs;
- industry-specific illustration;
- project-specific imagery;
- custom visual treatments.

But this should only be explored after the core Crush system is stable.

---

# 31 — SUCCESS CRITERIA

The system should be considered successful if:

- a new piece can be created without redesigning everything;
- different types of content can use the same underlying system;
- Original and Black can coexist without becoming unrelated systems;
- Social/documentary content can coexist with project/editorial content;
- website screenshots can be presented in multiple ways;
- Before/After can be optional;
- content can be reordered or emphasized differently;
- different formats can be supported;
- pieces remain recognizably Crush;
- pieces do not all look identical;
- the system can support future expansion;
- AI can understand and manipulate the system reliably.

---

# 32 — VALIDATION QUESTIONS

Before finalizing the architecture, answer:

1. What are the true non-negotiable visual characteristics of Crush?

2. Which elements are genuinely reusable?

3. Which elements are only specific to one existing reference?

4. Is Black Design a visual mode, composition family, or another structure?

5. Is Social Post a visual mode, content series, or combination?

6. Which content types actually need reusable structures?

7. Which compositions can accommodate multiple content types?

8. Which screenshot treatments are worth turning into components?

9. Which variations require variants and which should remain content changes?

10. How much flexibility is useful before the system becomes too loose?

11. What makes a client-adapted design still feel like Crush?

12. Which parts should remain intentionally constrained?

---

# 33 — AI WORKFLOW

Before building anything:

ANALYZE → CLASSIFY → PROPOSE → VALIDATE → BUILD

For the first step, do NOT build the final system.

First analyze the source material.

Identify:

- established brand rules;
- observed visual patterns;
- recurring structures;
- reusable elements;
- content-specific elements;
- project-specific elements;
- potential visual treatments;
- potential components;
- potential compositions;
- potential templates;
- ambiguities;
- contradictions;
- areas requiring human validation.

Clearly distinguish:

ESTABLISHED
from
OBSERVED
from
PROPOSED
from
HYPOTHESIS.

Never present a proposal as an existing Crush rule.

---

# 34 — FINAL PRINCIPLE

The goal is not:

"Make every Crush Instagram post look the same."

The goal is:

"Make different Crush Instagram posts feel like they belong to the same creative world."

The system should provide:

CONSISTENCY
+
FLEXIBILITY
+
RECOGNITION
+
SPEED

without sacrificing:

CREATIVITY
+
PROJECT DISTINCTIVENESS
+
HUMAN CHARACTER.

The system should make variation easier, not eliminate variation.
